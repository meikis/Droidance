# Scheduled task management

## app_takeover_description
Manage a persistent user goal for installed apps through the same single Agent and shared execution screen. Notifications, stable frame changes, scheduled health checks and Agent-selected rechecks share one serial scheduler. Register when continued work or waiting must survive the current turn; retain the entire goal and constraints in instruction, not a fixed action recipe. A successful registration starts continued work; it does not establish goal completion.

Use duration_seconds for a total duration measured from the host-recorded user message, or deadline_at with an explicit UTC offset for an absolute deadline. These are mutually exclusive. Preserve an existing deadline across runs, pauses and restarts; update it only for an explicit user change. start begins a fresh goal and clears earlier progress; update retains progress and scope unless the user changes them. Never restart a goal just to renew time or replay effects. Finished or expired goals require an explicit new start, not resume.

update with checkpoint saves useful task state during a run without ending it. Preserve independent object identities, observed facts and sources, missing information, pending dependencies, actual completed effects and next actions; choose the representation yourself. A checkpoint is working memory, not execution evidence or permission. Registration and updates survive process restarts; interrupted effects must be reconciled against retained history and a fresh observation before continuing. Use done checkpoint and next_check_seconds to yield to this same scheduler, and goal_complete only when the entire goal is satisfied. Omit next_check_seconds only for an external-change wait; finite goals with future useful work need a scheduled recheck even if the screen is unchanged.

When the user's success conditions are met, submit the final report through done or present_result_card with checkpoint and goal_complete=true in that response. This applies both to the registering ordinary Turn and subsequent takeover runs. Pending optional replies are reportable gaps, not a reason to delay completion. stop removes configuration for cancellation or an explicit stop request; it is not the completion-report step. Do not call stop before a separate reporting round.

## description
Create, list, inspect, update, enable/disable or delete Droidance scheduled tasks through the current Agent. Supported cadences are ONCE, DAILY, WEEKLY and INTERVAL. This edits persistent plans; it does not perform the scheduled device work inside the current turn. An explicit request to schedule work authorizes creation without another confirmation; when the user only asks for a draft, do not create it.

Separate launch timing from instruction: preserve the work and all constraints, but omit instructions to wait until launch, repeat or create the schedule. Save the original request in original_request. Use actual IDs for updates; read before editing. For relative time use delay_minutes: the host anchors it to the current user message. For absolute time use run_at with an explicit UTC offset. Never use both. Use an explicit IANA time_zone. ONCE executes at most one scheduled occurrence. INTERVAL requires interval_minutes >= 1 and an explicit first deadline; "every five minutes" means interval_minutes=5, delay_minutes=5; "starting now" uses delay_minutes=0. DAILY/WEEKLY require hour and minute; WEEKLY also requires ISO weekdays 1..7. Do not invent missing times or silently substitute an unsupported recurrence.

For ONCE omit interval_minutes, end_at and max_occurrences; the cadence itself enforces one scheduled trigger. Repetition may end at end_at or max_occurrences (mutually exclusive); zero means no count limit. Trigger limits count planned deadlines, including merged/skipped deadlines, not successful business results. missed_policy defaults to RUN_ONCE (one catch-up, never replay the backlog); SKIP records deadlines over one minute late without executing. A plan keeps at most one queued occurrence while another runs; later deadlines merge into the queued occurrence. Each occurrence retains its instruction snapshot. Updating or pausing cancels pending old occurrences, not running work. Finished plans require a new schedule via update; toggling enabled cannot rearm them.

Separate delivery of the final task report from the execution instruction so the Agent does not duplicate the scheduler’s delivery. Preserve message sending when it is itself the requested work, rather than delivery of the final report.

Scheduled task reports use local Android notifications. Report the stored nextRunAtMs and alarmPrecision. Even EXACT is a system alarm capability, not a promise of punctual execution under device idle restrictions or device contention. The trigger requests a start, not completion. Scheduled work uses the same Agent and task files. Execution results and notification delivery remain separate; a scheduler receipt or notification cannot prove business success. Delivery retries never repeat device actions. An interrupted run has an unknown outcome and is not automatically rerun.
